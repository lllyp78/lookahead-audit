# 时间与数据版本契约

审计的最小单位是一次决策，而不是一个交易日。先识别该决策能看到的每条输入，再追问这些输入的具体版本何时可用。

| 字段 | 含义 | 常见误区 |
| --- | --- | --- |
| `event_time` | 价格发生、统计期结束或事件生效的时间 | 把财报期末当成公告时间 |
| `available_at` | 该数据版本最早可被策略获得的时间 | 只按行日期截断 |
| `revision_at` | 修订值或回填值进入数据源的时间 | 用今天的修订值重放多年前的决策 |
| `decision_at` | 计算信号、仓位或风控动作的时间 | 认为“同一天”总有固定先后 |
| `selection_at` | 决定排序、入选集合、目标仓位的时间 | 把“选择”和“下单/成交”混成一个时点 |
| `order_at` | 订单生成并送达市场的时间 | 用成交后的信息决定订单 |
| `fill_at` | 成交模拟发生的时间 | 把触发条件和成交放在同一不可实现的价格点 |

核心约束：一个输入只有在其相关版本的 `available_at <= decision_at` 时才可用于该决策。信号还须先于订单；订单与成交关系由具体订单类型、市场规则和回测引擎定义。时间相同仍要检查事件顺序与处理延迟。

## 建模步骤

1. 记录市场日历、时区、bar 起止时刻，以及回测框架对 bar 标签的定义。
2. 列出策略的决策节点。跨资产、跨频率、外部数据分别记录可用时间。
3. 追踪从原始数据到缓存、因子、模型、信号和订单的加工链。每步变换都要保留“最早可用”约束。
4. 对历史重放，确认读取的是决策时能得到的版本。缺少发布或修订记录时标为证据不足，写清所作假设。

## 对照示例

| 场景 | 判定依据 |
| --- | --- |
| 10:05 读取 10:00–10:05 的完整 bar | 先确认 bar 在 10:05 已结束并送达策略；还要确认订单发生在其后。 |
| 收盘后用当日完整日线计算下一笔订单 | 当日数据可合法使用；下单和成交仍须按实际顺序。 |
| 开盘时用当日最终成交量筛选当天订单 | 最终量通常尚未生成，属于未来输入。 |
| 用 2023 年报的期末日期过滤财报 | 应使用该版本的公告/到达时间，修订值另计。 |
| T 日信号在 T+1 收盘成交 | 可能是合法的预先下单或收盘竞价模型；需核对订单形成与可实现成交机制。 |

## 盘中子决策示例（A 股）

日频策略也可能在盘中做选择；`selection_at` 必须精确到分钟。

| 时点 | 已知 | 尚不可用 |
| --- | --- | --- |
| 9:25 集合竞价结束 | 开盘价、竞价成交量/额 | 9:31–10:00 窗口额、9:45 价 |
| 9:45 | 9:45 价格快照 | 10:00 前的完整窗口额 |
| 10:00 | 9:31–10:00 完整窗口额 | — |

选择在 9:25，就只能用竞价数据；9:45 的价和 10:00 的窗口量不能进入排序。同一列在不同 source/leg 上可能有不同的 `available_at`，按行/来源分别建模。

不同资产不必有相同的最后观测日期。关键是各资产的当前值在决策时已经可用，且缺失、滞后和填充规则在历史与实盘中一致。策略如果依赖“最新”版本或模型文件，需追溯该文件的生成时间与上游训练数据。
